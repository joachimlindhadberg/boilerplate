# QA1 4A.6.9h – Responsive Image Processing & Optimization

**Base:** locally approved 4A.6.9g. **Status:** test candidate only; local user QA required. Public V2.5.0 remains NO-GO.

## Behavior

- Newly uploaded JPEG, PNG and WebP images retain their original files and their existing `media` DB row, ID, and URL.
- When PHP GD (JPEG/PNG/WebP supported) or Imagick is available, the upload processor creates up to three smaller, **non-cropped** images, with longest sides **320, 768, 1536 px**. It never enlarges an image.
- A small adjacent `original.ext.variants.json` file records public paths and dimensions. This file is upload data, not executable PHP. It is backed up and restored with the existing uploads tree; **no new table or database migration** is needed. Core media records expose parsed variants when present.
- Frontend Gallery and both Page Builder render paths add responsive `srcset` and conservative `sizes="100vw"` hints; theme owns all layout and CSS. Lightbox links still target the original file. Admin grid and Gallery Editor prefer thumbnail files.
- Deleting an unreferenced media record removes original, generated variants, and manifest after the existing DB/reference checks; batched-upload DB rollbacks similarly clean generated files.
- Existing files with no generated variants, legacy `/assets/uploads/` paths, GIF animations and videos continue working normally. Missing or invalid derivative files are never emitted in responsive markup.

## PHP and host limitations

- GD or Imagick is **optional** for normal uploads, but necessary to generate variants. When neither is available, original uploads succeed and optimization is skipped; Site Health reports the missing editor. Hosting PHP extension availability may differ from CLI PHP.
- Source MIME stays unchanged; no WebP conversion or original replacement in this release.
- JPEG sources carrying a non-default EXIF orientation are left unoptimized to avoid incorrectly rotated derivatives; original display remains unchanged.
- Large or memory-constrained images may be skipped safely. Failed optimization does not fail a valid original upload. PNG sizes may not always compress better than originals.
- Existing media are **not automatically backfilled**. New uploads get variants; older media can be re-uploaded or processed by a separately reviewed migration tool later.
- No JS, third-party image CDN, background worker, PHP shell/exec or additional webroot folder is introduced.
- `sizes="100vw"` is a safe, conservative hint independent of themes. A later theme-aware `sizes` contract may reduce bandwidth further.

## WordPress reference (user-supplied 7.1.3 source)

- `wp-admin/includes/image.php`: `wp_create_image_subsizes()` and `wp_generate_attachment_metadata()`.
- `wp-includes/media.php`: `wp_calculate_image_srcset()` and `wp_get_attachment_image_srcset()`.

The CMS reimplements only the relevant behavior; no WordPress source code is included or copied.

## Local QA (isolated site, no production DB)

1. Ensure PHP running the site has GD or Imagick (check the new Site Health report entry).
2. Use a **fresh isolated test site**, upload a JPEG photo wider than 1536 px, e.g. 4000×3000. Verify `original.jpg`, `-320px.jpg`, `-768px.jpg`, `-1536px.jpg` and `.variants.json` in the same `/uploads/YYYY/MM/` folder.
3. Upload a **small** image (no upscaling), a transparent PNG, an animated GIF, and a video; verify that the media library accepts the originals and GIF animation/video behavior is unchanged.
4. In Page Builder and Gallery, inspect the frontend `<img srcset>` and test responsive browser downloads; open Gallery lightbox to confirm it still uses the original.
5. Delete an **unused** image; check that its original, manifest, and variants disappear. Referenced media must still be protected from deletion.
6. Back up a site with generated variants, inspect the archive, and restore **only in an isolated environment**; check that all responsive URLs resolve. Existing pre-4A.6.9h backup/restore rules remain in force.

No public-host deployment, MySQL integration, live image upload or rollback has been performed within this candidate build.
