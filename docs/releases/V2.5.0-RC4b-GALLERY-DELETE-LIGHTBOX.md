# Boilerplate CMS V2.5.0-RC4b — Gallery Delete Actions & Lightbox

Status: **Development/Production Candidate — not user-approved**. Based strictly on the user's locally approved **V2.5.0-RC4a**. RC5 remains **not started**. The internal CMS version remains **2.5.0** across the Release Candidates; the final V2.5.0 Stable is not yet production-approved. The generic read-only upgrade preflight demands a strictly higher *core version* and therefore cannot compare two V2.5.0 RC ZIPs without flagging a version-only mismatch; verify migration immutability separately (all previously approved 11 file hashes remain pinned in the source audit).

## Scope

1. **Gallery list:** One Core `AdminListUI::actionGroup` per row with Edit and Delete. Delete is a non-submitting action opening one Core `AdminDeleteDialog`, outside the live-search replacement area. The `admin.js` shared handler safely writes an integer ID and inert gallery name to the form. The existing `/admin/gallerier?screen=edit` POST handler, `admin_verify_csrf`, repository page-usage protection and `media` retention are unchanged.
2. **Gallery edit:** The previously loose delete button becomes a `admin-panel admin-danger-zone` section styled with shared Core controls, matching Pages' delete zone. The same original editor delete dialog and server action remain.
3. **Optional gallery Lightbox:** Core `AdminToggle` in the Gallery publish settings. Stored in new `module_galleries.lightbox_enabled TINYINT(1) NOT NULL DEFAULT 0`; existing galleries default to **off**. When enabled, images render as real `<a href>` anchors with opt-in `data-gallery-lightbox-image` behavior and escaped/localized labels; when disabled, old `<img>`-only output is preserved. One reusable, accessible native `<dialog>` per page uses previous/next buttons, arrow keys, Escape, text-only captions, restored focus and progressive link fallback. The optional JS is registered by `ModuleFrontendScriptProviderInterface`, **without module-owned frontend CSS**; all visual styles live in `public_html/assets/scss/components/_components.gallery.scss` and the synchronized compiled theme CSS.

## Migration and deployment

**DO NOT run `verify-fixture`, any seed, or any data-changing test against the active CMS database.**

- One **new**, restart-safe migration has been added: `modules/gallery/migrations/20261019_100_gallery_lightbox.php`. It checks `INFORMATION_SCHEMA` before adding the column. All 11 previously approved migration files remain byte-identical.
- The standalone fresh-install baseline (`database/install/empty-schema.sql`) includes the new column; `FirstInstall::stampMigrations` explicitly recognizes and stamps the sixth PHP migration. The integration fixture schema is also updated (only synthetic fixture data).
- `modules/gallery/module.json` is advanced from `1.0.13` to **`1.0.14`** because runtime behavior changes. Gallery module activation/update is **explicit**, not automatic.

### Safe local/staging verification order

1. Make verified backups of existing DB, `.env`, uploads, and the approved **RC4a ZIP**. Ideally restore to a **separate, disposable clone** for validation.
2. Unpack the entire **RC4b Development Candidate** over the *test clone's code*, **preserving `.env`, database, uploads and existing runtime files**.
3. Inspect pending migrations read-only with `php core/cli/migrate.php --status`. Expect only `module:gallery:20261019_100_gallery_lightbox` pending; stop if other unexpected pending/mismatch results occur.
4. **Only after explicit review and backup, on the clone:** run `php core/cli/migrate.php --apply` to add the single column. This is intentional DDL; never execute it merely to run QA.
5. In `/admin/modules`, use the Gallery module's explicit update flow to acknowledge module version `1.0.14` after the migration is applied. Confirm Gallery is active and frontend works.
6. Verify Gallery list delete confirmation, Gallery edit danger zone, active gallery with Lightbox on/off, multiple galleries on one page, keyboard controls, anonymous frontend view, and that deletions used in Page Builder remain blocked.
7. Run **only the read-only** `sh tests/integration/run.sh verify-code` on the installed clone.

For a **brand-new** installation with RC4b, the browser wizard provisions the new baseline and stamps the reviewed migration; existing installation steps are not needed.

**Rollback:** Keep RC4a source ZIP. The additive database column is intentionally not automatically removed on rollback. Module version records may require deliberate reconciliation with the restored files. Never drop the column or blindly downgrade the DB in a production environment.
