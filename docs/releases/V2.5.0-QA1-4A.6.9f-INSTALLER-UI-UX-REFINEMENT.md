# QA1 4A.6.9f — Installer UI/UX Refinement (test candidate)

**Based on:** Locally user-approved 4A.6.9e Keyless Installer. **Status:** test candidate; user acceptance pending; public V2.5.0 NO-GO.

## Scope and UI
- A standalone 3-step installation wizard with a **fixed modal header and footer**. Only the central form pane scrolls. Modal is width-capped at 552px and height-capped at 680px within the available viewport; mobile uses near-full-height layout.
- Footer always shows the appropriate actions: Step 1 **Test connection**, Step 2 **Back / Install CMS**, Step 3 **Go to administration**. Footers use external HTML `form` association; the hidden default submit ensures Enter goes to **Install**, not **Back**.
- Compact named progress steps (Database / Website / Complete), semantically marked active step with `aria-current="step"`.
- Focusable error summary at the top of the scrollable body, focused by progressive enhancement. Existing PHP messages and preflight restrictions remain.
- `Show / Hide` password controls for DB and administrator; when JavaScript is disabled these controls remain hidden and native password inputs continue to work.
- Back preserves verified DB connection settings in private PHP session (without echoing the database password). If the database host/name/port/username remain unchanged, the same private password is reused after a blank password submission. Any change to those fields requires entering a password again.
- Back also preserves website/admin **non-secret** draft values. Administrator password is not saved in a draft and must be reentered.

## Unchanged security/data boundaries
- Keyless first-visitor takeover risk is unchanged: an unconfigured publicly reachable host does not cryptographically verify ownership. Restrict public access until installation is finished when needed.
- HTTPS restriction, private webroot enforcement, `HttpOnly`/`Secure`/`SameSite=Strict` installer session cookie, CSRF, session rotation after DB test, fresh empty DB/InnoDB checks, mandatory hosting preflight twice, installer lock after `.env` creation, and locking/rollback restrictions remain.
- No database schema or migration changes. No modification of media/upload paths, Core admin component styling or frontend CSS. `install.scss` and `install.css` remain byte-identical.
- Added `/assets/install.js` served under `script-src 'self'` with no inline scripts or remote code.

## Suggested local QA
1. Preserve your accepted 4A.6.9e unchanged. Unpack **4A.6.9f DEV** in an **isolated new local site**, pointed at a **new empty database**. Do not overwrite an existing `.env` or installed CMS.
2. At **Database**, open hosting requirements and scroll them. **Header and Test connection footer must remain visible**. Check mobile/narrow and short-height viewports.
3. Test DB connection. At **Website**, enter some values. Click **Back** and confirm database host, name, port, username remain populated but password does not appear. With database settings unchanged, leave DB password blank and select **Test connection** to reuse the server-held verified password.
4. Confirm website/admin text fields are restored. **Administrator password must be entered again**. Validate Show/Hide, keyboard Tab/Enter, and the end-to-end fresh installation.
5. Confirm 25 InnoDB tables, 9 triggers, admin login/logout and post-install redirect from `/install.php` to `/admin` as on the previous release. Do not test new installation against an existing live database.

**Limitations:** No full fresh-install MySQL run on the user's local machine and no external shared-webhost/browser-zoom or assistive technology audit performed for this candidate. This must be explicitly accepted by the user after local testing.
