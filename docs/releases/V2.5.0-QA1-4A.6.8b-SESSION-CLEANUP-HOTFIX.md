# V2.5.0-QA1 — 4A.6.8b Session Cleanup & Revocation Hardening

**2026-10-24 · ISOLATED QA CANDIDATE · NOT PRODUCTION APPROVED**

Base: cumulative 4A.6.8a Session Manager package. Existing `auth_sessions` database table from 4A.6.8a is required. **NO NEW SQL migration.**

## Problem reproduced during local QA

- A browser can lose its `PHPSESSID` while retaining its Remember Me cookie.
- A subsequent password login could replace the browser's local session binding without revoking the previous database row and Remember Me credential.
- Older `auth_sessions` rows containing an unexpired Remember Me hash may remain until independently revoked or expired.
- A cookie still bearing the name `PHPSESSID` after logout is expected: the login page may create a fresh anonymous PHP session; cookie *values* should rotate.

## Production changes

1. `Auth::login()` revokes previous current-browser PHP and Remember Me bindings *after successful credentials* but before generating a fresh login. Separate devices are not touched.
2. `Auth::logout()` attempts to revoke both the current PHP binding and a provably browser-held Remember Me token. This also works when the browser's PHP session has been deleted. The cookie and PHP session are cleared as before.
3. `SessionManager::revokeRemember()` deletes exactly one row matched by the cryptographically unguessable Remember Me token hash and user ID. No user-wide deletion.
4. `SessionManager::cleanupAbandoned()` deletes only rows whose last activity is older than the greater of 48 hours and configured PHP session timeout plus 24 hours **AND** which lack an unexpired Remember Me credential. This runs opportunistically after successful login/remember recovery; it is not a cron task and does not run on every request.
5. `Auth::discardLocalBinding()` also clears the request's touch throttle marker so it cannot be reused for a new login.

## Scope limits / security notes

- **No automatic deletion of unexpired Remember Me tokens from devices whose browser cookie is no longer available.** An old orphan like local ID 4 may remain until expiry. Revoking all user logins through existing credential-change controls also clears such rows. Arbitrary forced cleanup risks logging out legitimate devices.
- The cleanup threshold adapts to the CMS `session_timeout` setting, avoiding surprising logout when configured longer than 48 hours.
- Login and per-device logout still rely on database availability for durable revocation; database failures are logged. Local cookie deletion by itself does not guarantee server-side revocation if MySQL is down.
- Existing 4A.6.8a database migration is still a prerequisite. Never run the migration again against an already-migrated database, and **never import an entire database backup** to apply this code-only hotfix.
- Historical RC5b remains the previous stable development reference. The cumulative 4A.6.8a is still not approved; no current QA package is ready for public release.
