# Boilerplate CMS V2.5.0-RC5 – Customizable Dashboard Cards

**Status:** Development and production candidates, awaiting explicit user acceptance. The approved rollback reference remains V2.5.0-RC4b. **Not a Stable Production release.**

## Scope

- All four existing metric cards retain their size, color, Core styling and default selection/order.
- "Tilpas kort" opens a compact inline editor with four native select controls and explicit save/cancel.
- Choices: Published pages, Drafts, Scheduled, Media, All pages, Forms, Submissions and Galleries.
- Forms and Submissions appear only when Forms is active. Galleries appears only when Gallery is active. All options are gated by the existing Core capability registry.
- Duplicate, unknown, malicious and unauthorized POST values are refused. The POST uses the existing admin CSRF token, authenticated session and server-side user ID; a successful save redirects back to Dashboard.
- Selections persist per account in `user_dashboard_cards` (one row per user, FK `ON DELETE CASCADE`). No LocalStorage or visitor-facing values. All counts are read-only and provider failures show `—`, not a misleading zero.
- Saved options from deactivated modules are replaced safely at render time, without silently rewriting the stored preference. Valid selections remain in their corresponding slots.
- No frontend/theme code, historical migrations, upload directories or existing user rows changed.

## Database changes (explicit migration)

New migration: `core:20261019_200_dashboard_cards` (`database/updates/20261019_200_dashboard_cards.php`). Adds **only** the new preference table and does not modify existing tables or records. MigrationRunner remains CLI-only; ordinary admin requests never apply schema changes. The RC2 fresh-install baseline includes the new table, with `FirstInstall::stampMigrations()` updated to verify its checksum.

For an **isolated test installation**, take a backup and check `php core/cli/migrate.php --status`; then explicitly run `php core/cli/migrate.php --apply` **only after verifying the target test database and user**. Check the status again, log in, and test changing card 1–4. **Do not run `--apply` on an active/production database as part of the RC5 acceptance test.** Without the new table, the dashboard displays its old default cards and a diagnostic notice; saving requires the reviewed migration.

## Acceptance tests

1. New user sees Published, Drafts, Scheduled, Media, unchanged visually.
2. Select four different metrics and Save. Reload and confirm persistence.
3. Log in with a second editor/admin account and confirm independent defaults/selections.
4. Duplicate a metric: accessible validation; server rejects duplicates even with JavaScript disabled.
5. Enable Forms/Gallery and select metrics; deactivate module: unavailable metrics are replaced safely and URLs to inaccessible modules do not appear.
6. Ensure cards navigate to actual authorized admin routes, and numbers show totals from the corresponding DB tables.
7. Test 320px/mobile and desktop. No modal, overlays or frontend CSS changes.
8. Run `sh tests/integration/run.sh verify-code` (read-only), and optionally live UI checks against a **separate** test site.

## QA boundaries

The included PHP regression suite, static source audits and isolated in-memory account tests do not run the new migration against a live MySQL server or validate real browser flows with a connected DB. Explicit local MySQL test, staging and production sign-off remain pending. All historical migrations were preserved byte-identically relative to RC4b.
