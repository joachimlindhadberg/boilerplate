# Boilerplate CMS V2.5.0-RC4 – Frontend Admin Topbar

**Status:** Development/Production **candidate for local review**, not stable or production approved.  
**Base:** V2.5.0-RC3 – Frontend Markup Hardening (user approved).  
**CMS version:** `2.5.0` (unchanged).  
**Scope:** Phase 4 only. No Dashboard Cards feature, migration, public Page Builder changes, or changes to admin styling.

## Functional changes

- Core provides `FrontendAdminBar`, invoked only for normal public HTML page responses after endpoint/redirect/maintenance handling and active module boot. Public `header.php` renders it immediately after `<body>` and before the site's own header.
- Ordinary visitors are never shown a toolbar. Frontend login identity, role, token expiry and remember-me are verified using the existing `Auth` service, not an untrusted session-role string. Users required to change their password do not see privileged shortcuts.
- Logged-in users with `admin.access` can open the CMS Dashboard and the native account disclosure. `content.manage` additionally enables **New page**, and **Edit page** only for genuine published/protected Core page records with positive IDs; 404 and module public routes have no edit shortcut.
- Account disclosure shows a safely escaped user name, a Dashboard shortcut and **Log out**, posting to the unchanged `/admin/index.php?mode=logout` route with its existing server-recognized CSRF token. No new public write endpoint.
- Text labels use existing Core translations plus three RC4 keys across all five admin languages. Mobile layouts retain real accessible link labels while presenting icons compactly; `<details>` works with a keyboard without new JavaScript.
- Semantic toolbar HTML is generated by Core using fixed icon definitions. **Only the frontend theme** provides toolbar CSS (`assets/scss/components/_components.admin-bar.scss`, imported in `style.scss`, synchronized with `assets/css/style.css`). Modules gain no CSS or inline styling.

## Cache and session security

- Every public **HTML page** response adds `Vary: Cookie`. When an existing session is active or a login/remember cookie is provided, the page emits `Cache-Control: private, no-store, no-cache, must-revalidate, max-age=0` and `Pragma: no-cache` before any page HTML.
- Forms already starts a PHP session on public requests. RC4 explicitly differentiates an **anonymous Forms session** from an authenticated session, preventing unnecessary Auth/Users queries on each anonymous visit. It still sends no-store for session-associated HTML.
- PHP cannot force a misconfigured reverse proxy/CDN to honor `Vary`, cookies or `no-store`. **Before production**, bypass all shared HTML caching for requests with session/remember cookies; test logged-in/logged-out and separate users through the actual proxy. Never serve cached authenticated HTML to anonymous visitors. Static assets retain their existing cache policy.
- Existing protected-page access, session timeout, remember-me, login/logout, admin capability controls and CSRF processing remain with the original Core services.

## Verification

Safe source-only checks:

```sh
sh tests/integration/run.sh verify-code
sh tests/integration/run.sh verify-production
```

The new isolated regression checks the real Core renderer (permissions-driven variations, escape safety, translations, 404/modules, POST/CSRF logout, integration gates and anonymous session behavior). It is run automatically by `verify-code`. These tests **do not** run active DB queries, migrations, fixture builds or live HTTP. The development environment lacks `mysqli`/`mbstring`/connected MySQL, so manual local integration remains important.

### Manual acceptance matrix on an isolated local site

1. **Logged out:** view homepage, content pages and 404. No topbar HTML or account links. Check navigation and layout still work.
2. **Logged-in admin:** topbar visible; Dashboard, New page and Edit page on a real published page. New/edit URLs go to the existing administration. No Edit page on a 404 or a module public URL.
3. **Editor:** test expected Dashboard, New/Edit and account actions. For any account without content permission, New/Edit must be absent. Test a user with forced password change and a deactivated/expired login.
4. **Account:** open with mouse and keyboard, verify the escaped display name, press Log out; after logout, refresh the public page and confirm there is no toolbar. Confirm CSRF-less requests to logout don't log the user out.
5. **Mobile:** test 320–768 px, landscape and keyboard navigation. No layout overlay or horizontal document overflow. Existing site header and navigation remain independent.
6. **Caching:** inspect `Vary: Cookie`, and authenticated `Cache-Control: private, no-store...`. Test one logged-in browser and one anonymous/private browser through your actual proxy/CDN configuration before public launch.
7. Run the read-only `verify-code` test on your Mac. Do not use `verify-fixture` against your active database.

**Rollback:** The previously accepted RC3 remains the approved baseline until you explicitly approve RC4; preserve existing database, `.env` and uploads during local candidate testing.
