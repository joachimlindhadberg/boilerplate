# V2.5.0-QA1 — Dashboard Getting Started: installation-scoped dismissal

**Status:** Isolated test candidate, not production approved.
**Baseline:** V2.5.0-QA1 Dashboard Getting Started test candidate; includes all previously isolated 4A.6.2a/4A.6.3/4A.6.3a/4A.6.3b and English Default work.

## Problem

The v3 browser preference used only the numeric user ID. A new installation on the same host can reuse user ID 1, so the old installation's dismissed state concealed Getting Started before the new admin first saw it. Testing in Incognito hid the root cause rather than fixing the key namespace.

## Patch

- Fresh browser installations receive a new public, random 128-bit `CMS_SITE_INSTANCE_ID` recorded in private `.env` by the existing installer. The full `.env` text and its random identity are generated **before** database DDL. The instance ID is not a credential and must never be used for authorization.
- The dashboard view publishes only a validated 32-character lowercase hex instance ID in `data-site-instance-id`; no .env secrets are sent to the browser.
- `admin.js` stores a dismissal as `boilerplate.admin.dashboard-welcome.v4.instance-<id>.user-<id>` when the new site identity is available.
- Earlier v3/v2 browser preferences are not imported into a newly created site instance, so a new site with the same domain/user ID gets Getting Started on first dashboard visit.
- Existing sites that have no `CMS_SITE_INSTANCE_ID` retain v3/v2 preference semantics, avoiding unexpected onboarding after a normal code update.
- No database schema change, no backfill of existing `.env`, and no server-side writes during dashboard GET. No changes to UI appearance, permissions, scheduled tasks or modules.

## Limitations and acceptance

- To test this branch end to end, make a **fresh, isolated** installation using this candidate. An existing `.env` from an older release has no `CMS_SITE_INSTANCE_ID` by design and remains in legacy mode. Do not add or rotate IDs in an existing production `.env` merely to test.
- On a fresh install, open the dashboard in the **regular** browser profile previously used to dismiss a welcome panel at the same host. The Getting Started panel must open. Close it, refresh and log in again; it must stay closed. Use **Show welcome** to reopen. No direct database imports or application overwrites on existing sites.
- On shared hosting, PHP's production `APP_ENV`, HTTPS and private webroot policies still apply. A local source or synthetic browser test does not certify hosted production behavior.
- LocalStorage remains per browser/device; cross-device once-per-user preference would need separate design and tests.
- Restoring a private `.env` along with its original site preserves the instance identity by design; manually reusing an existing `.env` for an unrelated new database is not a supported fresh install path.

## Testing

- New source-only PHP contract `tests/dashboard-instance-id-qa1.php` checks uniqueness, validated rendered marker, early config generation, and legacy isolation without DB operations.
- New Chromium regression `tests/browser/dashboard-instance-id-qa1.py` checks old v2/v3 state, two fresh installations with the same browser and numeric user ID, local dismissal, manual restore and legacy fallback.
- Existing Getting Started PHP and Chromium tests remain unchanged and pass after the test fixture accepts the new optional installation ID.
